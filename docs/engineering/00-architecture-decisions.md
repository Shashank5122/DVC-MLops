# SignalGEO — Engineering decisions (M1)

**Status:** implemented and tested as of 17 Oct 2026 (Milestone 1)
**Scope:** the decisions below cover the M1 codebase only. Measurement, evaluation and reporting
arrive in M2 and will need their own recorded decisions.
**Authority:** this document does not override anything in `docs/INTEGRITY-RULES.md`,
`docs/validation/08-compliance-decision-sheet.md` or `docs/validation/00-integrated-plan.md`.
Where it touches provider use, the compliance sheet governs.

Every entry states the decision, the reason, the alternative rejected, and what would make us
revisit it. Decisions marked **[compliance]** exist because of a licensing restriction, not
because of a technical preference.

---

## ADR-01 — One service, one database, no orchestration

**Decision.** A single FastAPI application with one PostgreSQL database, plus one Next.js
frontend. No microservices, no message queue, no Kubernetes, no agent framework, no service mesh.

**Reason.** The founder's brief explicitly rules out premature microservices and complex agent
orchestration, and integrity rule 13 requires that agents be used only where they demonstrably
beat a simpler alternative. At pilot scale (a handful of workspaces, hundreds of observations) a
queue and a scheduler add failure modes without adding capability. Everything M1 does is a
synchronous request/response.

**Rejected.** (a) Separate ingestion worker + API: justified only once observation volume or
provider rate limits force asynchronous collection — that is an M2/M5 question. (b) Celery/RQ:
same. (c) LangGraph or any agent framework: no part of M1 needs multi-step autonomous reasoning,
and the workflow that eventually will (M3 recommendations) is explicitly *not* autonomous — it
ends at a human approval gate.

**Revisit when.** M2 ingestion needs scheduled collection windows, or provider rate limits make
synchronous collection impossible. Even then, prefer a single-process scheduler over a second
service.

## ADR-02 — Synchronous SQLAlchemy 2.0, not async

**Decision.** Sync `Session` and sync engine. FastAPI runs the sync route functions in its
threadpool.

**Reason.** Async SQLAlchemy doubles the surface for mistakes (lazy-load in an async context,
session lifecycle across awaits, driver compatibility) for a workload that is dominated by small
indexed queries. The pilot will not be I/O-bound on the database. Fewer moving parts is worth more
than theoretical concurrency here.

**Rejected.** `asyncpg` + `AsyncSession`. It would also have forced a second set of fixtures and a
different test strategy.

**Consequence, recorded honestly.** Throughput per process is bounded by the threadpool. If a
future measurement run needs hundreds of concurrent provider calls, the right answer is a separate
collector process (ADR-01's revisit condition), not converting the API to async.

## ADR-03 — PostgreSQL in production, SQLite for the test suite

**Decision.** The application reads one `SIGNALGEO_DATABASE_URL`. `docker-compose.yml` supplies
PostgreSQL 16. The test suite runs against a per-test SQLite file. One test module
(`tests/test_migrations.py`) verifies that the Alembic migration produces exactly the schema the
models declare, and reverses cleanly.

**Reason.** Tests must run with zero services present — including in this sandbox, which has no
PostgreSQL server and no Docker daemon. Portable column types make that possible without a second
schema definition.

**How portability is achieved.**
* `sa.Uuid` → native `uuid` on PostgreSQL, `char(32)` on SQLite.
* `sa.JSON().with_variant(JSONB(), "postgresql")` → `jsonb` where it matters, text elsewhere.
* `Enum(..., native_enum=False)` → `VARCHAR` + a CHECK constraint, so no PostgreSQL enum type has
  to be created, altered or dropped in a migration. This is a deliberate trade: we give up
  database-level enum typing in exchange for migrations that are safe on both backends and that
  never need `ALTER TYPE` gymnastics.
* `render_as_batch=True` in Alembic, because SQLite cannot alter most constraints in place.
* A deterministic naming convention for constraints (`uq_`, `fk_`, `ix_`, `ck_`, `pk_`), so
  autogenerated and hand-written migrations agree.

**What is NOT verified here.** No PostgreSQL server exists in this sandbox, so the PostgreSQL path
is exercised only in CI (`backend-postgres` job in `.github/workflows/ci.yml`, which runs
`alembic upgrade head` and the full suite against `postgres:16-alpine`). Locally the
postgres-marked test is **SKIPPED**, never silently passed. Integrity rule 18 applies: we do not
claim a test passed unless it ran.

**Revisit when.** Never for the schema strategy. If SQLite/PostgreSQL behaviour divergence ever
bites (JSON semantics, `LIKE` case sensitivity, UUID ordering), the fix is to run the suite against
PostgreSQL in CI and keep SQLite as the fast local path — which is already the arrangement.

## ADR-04 — Pilot tenancy: a hashed workspace key in a header, with schema-level isolation

**Decision.** A tenant is a `workspaces` row. Requests identify the tenant with
`X-Workspace-Key: sg_…`. The key is stored **only** as a SHA-256 hash (plus the last four
characters, for display). Every tenant-owned table carries a non-null `workspace_id` foreign key,
every uniqueness constraint is composite on `workspace_id`, and every service function takes
`workspace_id` as an explicit argument and filters by it.

**Reason.** The brief scopes auth and tenancy to a pilot: no enterprise SSO, no complex billing,
no user accounts. What cannot be deferred is the *isolation boundary*, because leaking one client's
brand data to another would be a real commercial and legal failure. So the boundary is enforced in
the schema and in every query, and it is tested as a security boundary
(`tests/test_tenancy_isolation.py`, 8 tests) rather than as a feature.

**What this is not.** It is not authentication in any meaningful sense. There are no users, roles,
sessions, password resets or MFA. Possession of a key is the whole credential.

**Controls that do exist.**
* Keys are generated with `secrets.token_urlsafe(32)` and printed exactly once
  (`scripts/bootstrap_workspace.py`, or the development-only HTTP endpoint).
* An unknown key and a malformed key produce the same `401 UNAUTHENTICATED` message, so the
  endpoint cannot be used to enumerate valid keys.
* `404` (not `403`) is returned when a valid key asks for another workspace's row, so cross-tenant
  probing cannot distinguish "exists but not yours" from "does not exist".
* HTTP bootstrap is refused unless `SIGNALGEO_ENVIRONMENT=development`
  (`403 FORBIDDEN` otherwise), and the production path is the operator-run script.
* Revocation = delete or suspend the workspace row; `suspended` workspaces are rejected at
  resolution time with `403`.

**Revisit when.** Before any real client data is entered, and certainly before M4's client-ready
report. The expected replacement is per-user accounts with a workspace membership table, keeping
the same `workspace_id` scoping — the schema already assumes it.

## ADR-05 — [compliance] Provider kill-switch and denylist, enforced in configuration

**Decision.** `SIGNALGEO_PROVIDER_CALLS_ENABLED` defaults to **false**. A `provider_denylist`
defaults to `gemini-grounding-google-search,perplexity-agent-api`. `ProviderRegistry.assert_permitted`
must be called before any adapter issues a request, and refuses when either control blocks it.
Production startup **fails** if `provider_calls_enabled=true`. No M1 code path performs network I/O
to any provider — the only registered adapter is a deterministic fixture.

**Reason.** `docs/validation/08-compliance-decision-sheet.md` finds that Gemini Grounding with
Google Search is prohibited for this use case on five independent grounds in the official Gemini
API Additional Terms (analyse / extract-or-collect for another purpose / other monitoring / create
a database / display only to the prompting end user), and that the Perplexity Agent API cannot be
used until three unverified items are resolved in writing (gate W2). A policy that lives only in a
document will eventually be violated by a well-meaning commit; a policy that lives in configuration
and is asserted in code fails loudly instead.

**Enforcement points.**
1. `Settings.provider_calls_enabled = False` and the denylist (config layer).
2. `_guard_production` model validator: production refuses both SQLite and an enabled switch.
3. `ProviderRegistry.is_permitted` / `assert_permitted` → `ProviderDisabledError` (`403`).
4. `/api/v1/providers` is **GET-only** and returns the current permission state, including the
   reason for each denial. `tests/test_providers.py` asserts no route in the whole API can trigger
   a collection call.
5. The frontend Providers page states the two denials and their reasons in the UI, so nobody
   discovers the policy by accident.

**Rejected.** (a) An environment variable alone, with adapters checking it informally. (b)
Registering real adapters "but disabled" — an adapter that exists will eventually be called. There
is deliberately **no** Gemini or Perplexity adapter class in this repository.

**Consequence for M5.** Adding a permitted integration requires: writing the adapter, removing the
provider from the denylist, flipping the switch, and recording the written authorization in
`docs/validation/`. That is a visible, reviewable diff, which is the point.

## ADR-06 — Measurement-shaped adapter contract, defined before any adapter exists

**Decision.** `app/providers/base.py` defines `ProviderAdapter` (`metadata`, `collect`,
`estimate_cost_usd`) plus the value types a measurement needs: `SurfaceKind`
(`api_search_enabled`, `consumer_interface_human`, `vendor_platform`, `ungrounded_model`,
`mock_fixture`), `CollectionMethod` (`official_api`, `human_transcription`, `vendor_export`,
`deterministic_fixture`), `Capability` (does it return citations? raw text? region/language?
repeat runs?) and `ProviderMetadata` (exact `model_identifier`, compliance status and notes).

**Reason.** The brief's measurement model requires that observations never conflate consumer
interfaces with API outputs, never blend providers into one unexplained score, and always carry
provenance. Those properties have to be *structurally* impossible to lose, which means the surface
and the collection method must be part of the adapter's identity rather than a field someone
remembers to set later. Defining the contract in M1 also means M2 ingestion has one typed target
and cannot drift.

**Not built.** The M2 storage tables for observations, evidence, extraction metadata, grounding
status and request costs are intentionally absent. Half-built measurement tables are worse than
none: they invite writes before the semantics are settled. `app/providers/mock.py` does return the
full observation payload shape (`prompt_hash`, `response_text`, `citations`, `mentions`,
`grounding_used=None`, `cost_usd`, `observed_at`) so the contract is exercised by tests.

**`grounding_used` is `None` for fixtures** and is typed to allow `true | false | unknown`. It is
never guessed — control K10 in the compliance sheet requires the three states to be reported
separately.

## ADR-07 — Append-only audit trail from the first table

**Decision.** `audit_events` records workspace, actor, action, entity type/id, a JSON `changes`
map, and the request's `correlation_id`. `app/services/audit.py` exposes `record()` and
`list_events()` only — there is no update or delete function. Every brand and competitor mutation,
and every authorization/verification flag change, writes an event inside the same transaction as
the change itself.

**Reason.** Integrity rule 16 requires auditability designed in, not bolted on, and rule 14
separates research, recommendation, approval, publishing and evaluation with separate permissions.
Those separations are only demonstrable if the record of who authorized what exists from day one.
M3's human approval workflow will depend on this table rather than inventing its own.

**Detail that matters.** Flag changes record `{from, to}` values, not just "changed". A reviewer
can therefore reconstruct when `website_change_authorized` was turned on and by which correlation
id — which is exactly the evidence a client dispute would need.

**Not built.** No retention policy, no tamper-evidence (hash chaining or WORM storage), no
export. For a pilot, database-level protection plus the absence of any delete path is proportionate.

## ADR-08 — Soft delete for brands

**Decision.** `brands.deleted_at` is set instead of deleting the row; all reads filter on
`deleted_at IS NULL`.

**Reason.** Once M2 attaches observations and evidence to a brand, a hard delete would destroy the
audit trail's referents and make a past client report unreproducible. Starting with soft delete
costs one nullable column and one `WHERE` clause; retrofitting it later would be a data migration.

**Consequence.** Uniqueness constraints still include soft-deleted rows, so a deleted brand's
domain cannot be immediately re-onboarded under the same slug. That is deliberate: re-onboarding
should be an explicit decision, not a silent collision.

## ADR-09 — Single error envelope, correlated to logs

**Decision.** Every failure returns
`{"error": {"code", "message", "details", "correlation_id"}}` with a `SCREAMING_SNAKE` code
(`NOT_FOUND`, `CONFLICT`, `VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`,
`PROVIDER_CALLS_DISABLED`, `DATABASE_UNAVAILABLE`, `INTERNAL_ERROR`, `HTTP_<status>`). Handlers are
installed for `AppError`, `HTTPException`, `RequestValidationError`, `IntegrityError`,
`SQLAlchemyError` and a final `Exception` catch-all. `X-Correlation-ID` is generated per request
(or accepted from the client), echoed in the response header, attached to every log line, and
stored on audit events.

**Reason.** A client-facing report will eventually need to say "this number came from this
observation, collected at this time, under this request". The correlation id is the cheapest part
of that chain and must exist before there is anything to trace. The catch-all matters for security:
an unhandled crash returns a generic `INTERNAL_ERROR` with no traceback, no SQL and no internal
paths — asserted in `tests/test_error_handling.py`, which deliberately raises an exception
containing a fake secret and checks that the secret does not appear in the response.

**Rejected.** FastAPI's default `{"detail": ...}` shape, which leaks framework internals in
validation errors and cannot carry a correlation id.

## ADR-10 — Structured JSON logging, no request bodies

**Decision.** One JSON line per log event with `ts`, `level`, `logger`, `message`,
`correlation_id`, plus per-call extras (`method`, `path`, `status_code`, `duration_ms`,
`workspace_slug`, error codes). `SIGNALGEO_REQUEST_LOG_BODY` defaults to **false** and is not used
anywhere in M1. Third-party loggers are quieted; `sqlalchemy.engine` only logs at `DEBUG`.

**Reason.** Brand names, domains and descriptions are client data. Logging request bodies would
put client business information into log aggregation, which is a data-handling commitment we have
not made and, per the compliance sheet's preference for *paid and documented* data-handling
arrangements, not one to make casually.

## ADR-11 — Frontend: Next.js App Router, hand-written CSS, server-side proxy

**Decision.** Next.js 16 + React 19 + TypeScript (strict, `noUncheckedIndexedAccess`), App Router,
client components only where state exists. All styling is hand-written CSS with design tokens in
`app/globals.css`. The browser calls **only** relative `/api/backend/*` paths; `next.config.ts`
rewrites them to `BACKEND_ORIGIN/api/v1/*`.

**Reason for the proxy.** It removes the backend origin from the browser entirely, so the app works
behind any host, reverse proxy or sandbox preview domain, and no CORS preflight is needed for the
UI. `BACKEND_ORIGIN` is a server-side value and never appears in a client bundle.

**Reason for hand-written CSS.** The brief says to challenge unnecessary dependencies. Tailwind,
shadcn/ui, Radix, a component library and a state library together would add several hundred
transitive packages to serve five pages. The UI needs tokens, a grid, a table, forms and pills —
749 lines of CSS covers it, is auditable in one read, and has no supply chain. Security headers
(`X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`) are set in `next.config.ts`.

**Rejected.** (a) Tailwind — real value at scale, negative value for five pages. (b) React Query /
SWR — the data fetching here is a handful of calls with `useEffect` + `AbortController`; a cache
layer would add invalidation questions we do not have. (c) Redux/Zustand — one workspace key in
`localStorage` is the entire shared state. (d) ESLint — deferred deliberately; `tsc --noEmit`
(strict) and `next build` are the gates. Recorded as a limitation, not an oversight.

**Known pilot limitation.** The workspace key lives in `localStorage`, so it is readable by any
script on the origin and is not rotated. This matches ADR-04's pilot posture and is stated in the
UI on the setup page.

## ADR-12 — Dependency floor

**Decision.** Runtime dependencies are exactly: `fastapi`, `uvicorn[standard]`, `sqlalchemy`,
`alembic`, `psycopg[binary]`, `pydantic`, `pydantic-settings`; frontend: `next`, `react`,
`react-dom`. Dev: `pytest`, `httpx`, `ruff`, `mypy`, `types-Pygments`, `typescript`, `@types/*`.
Nothing else.

**Explicitly not added, with reasons.**
| Rejected | Why |
| --- | --- |
| `httpx` at runtime / any provider SDK | No provider calls exist in M1 (ADR-05). An SDK in the image is an invitation. |
| `pydantic-settings` alternatives (`dynaconf`, `python-decouple`) | One settings class with validators is enough. |
| `fastapi-users`, `authlib`, `passlib`, `python-jose` | No user auth in M1 (ADR-04); these bring key-management surface. |
| `celery`, `rq`, `arq`, `apscheduler` | ADR-01. |
| `redis` | Nothing to cache; a cache would obscure measurement provenance. |
| `sqlmodel` | Adds a second abstraction over SQLAlchemy for no gain with typed 2.0 `Mapped[]`. |
| `pandas`, `numpy`, `scipy` | No statistics computed in M1. When M2 needs Wilson intervals, add exactly one library then. |
| `structlog` | The 40-line JSON formatter in `core/logging.py` does the job with no dependency. |
| `tailwindcss`, `shadcn/ui`, `@radix-ui/*`, `zustand`, `@tanstack/react-query` | ADR-11. |
| `playwright`, `vitest`, `jest` | No frontend test framework yet. Recorded as a **gap**: UI behaviour is verified only by type-check, build and manual exercise. Adding Playwright is the natural M4 QA step. |
| `docker`-compose plugins, `k8s` manifests, Terraform | ADR-01; the pilot runs on one host. |

## ADR-13 — Deterministic mock provider, not a stub

**Decision.** `MockProvider` is a real `ProviderAdapter` whose output is a pure function of the
prompt hash: same input → same output, always, with `cost_usd = 0.0` and no I/O. A
`fixture_fingerprint()` (SHA-256 of the fixture set) lets any later report state exactly which
fixtures produced it.

**Reason.** M2 ingestion, normalisation, entity resolution and evaluation all need to be tested
before any provider is permitted. A stub that returns random data would make those tests
flaky; a fixture-only mock makes them reproducible, which is the property the whole measurement
model is built on.

**Guard against a real mistake.** Mock observations carry `surface=mock_fixture` and
`collection_method=deterministic_fixture`. They can never be mistaken for a real measurement in
storage or reporting, and per the brief's rule about not blending surfaces, they must be reported
separately or not at all.

## What this architecture deliberately does not do yet

1. **No measurement storage.** No observation, query registry, evidence or extraction tables
   (M2).
2. **No evaluation or scoring.** No visibility index, no citation analysis, no statistics (M2).
3. **No recommendations or approvals.** No proposal objects, no approval state machine (M3).
4. **No report generation.** Nothing client-facing (M4).
5. **No integrations.** No Gemini, no Perplexity, no scraping of consumer interfaces, no vendor
   platform imports. Only the fixture adapter (M5, and only after separate authorization).
6. **No user authentication, no billing, no rate limiting, no HTTPS termination, no observability
   stack.** Pilot scope; rate limiting and TLS are the deployment's responsibility and are listed
   as limitations in the M1 report.
